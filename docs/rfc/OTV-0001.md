# OTV-0001 Problem Statement

**Status:** Accepted  
**Version:** 0.1.0

## Abstract

Users treat explorer activity as proof of received, spendable value. Attackers exploit that collapse. OTV is a vendor-neutral verification layer that answers a narrower question: *does this incoming event represent verified value for this recipient?*

## Motivation

Explorers correctly display chain data. They do not evaluate recipient spendability. Wallets and fintech apps need a deterministic, signed, evidence-backed verdict that does not require the user to interpret RPC concepts.

## Specification

1. Separate activity, execution, asset identity, recipient, amount, balance delta, finality, and spendability.
2. Never let an LLM decide spendability (ADR-008).
3. Produce `otv.verdict.v1` with evidence and an Ed25519 signature.
4. Adapter isolation: business logic never calls RPC directly.

Normative: `docs/VERDICT_SPEC.md`, `docs/THREAT_MODEL.md`, `docs/ARCHITECTURE.md`.

## Compatibility

Breaking changes to the public verdict schema require a new schema id, not a silent field reuse.

## Security Considerations

A technically true hash can still be economically false. OTV must not raise confidence for mock adapters. Production signing keys never leave the server.
